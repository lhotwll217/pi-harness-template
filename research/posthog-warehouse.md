# Can PostHog act as the data warehouse for a GTM agent harness?

Research ticket resolved against PostHog primary sources (posthog.com docs, pricing, roadmap; PostHog GitHub) on 2026-08-29.

**Verdict.** Yes for the *read/analytics* half, no for the *durable domain-state* half. PostHog's data warehouse (2026) natively syncs Google Ads, Google Search Console, Postgres, HubSpot, Salesforce, S3/GCS/R2/Azure object storage, and a generic Custom REST source — everything a GTM harness needs on the ingest side — and an agent can query all of it with HogQL/SQL over a documented query API (also via PostHog's MCP server), with 1M synced rows/month free. But the warehouse is a read-only sync target: PostHog explicitly says the `/query` endpoint is not an export mechanism, there is no API for writing arbitrary rows into warehouse tables (writes are limited to events, person/group properties, and file uploads), sync freshness is bounded by schedule (5 min at best, and some sources lag days), and free-tier retention is 1 year. A GTM harness would still need a separate durable store (e.g. Postgres) for its own domain records — lead state, agent decisions, pipeline stages — which can then be synced *into* PostHog as a source for analysis. PostHog's own CRM ambitions (open "PostHog CRM" issue, groups-as-CRM "Customer analytics" work on the roadmap) point the same direction but are not shipped product; do not plan on them.

---

## 1. Data warehouse / external sources today

PostHog's data warehouse "brings your business data into PostHog and puts it next to your product data": sync managed sources, then query them alongside events, persons, and sessions in one SQL query, "no ETL pipeline to build." Data comes from (a) managed sources, (b) PostHog's own tables (events, persons, sessions, groups, query log), (c) files and object storage (CSV/JSON/Parquet upload, or read straight from S3, GCS, Cloudflare R2, Azure Blob), and (d) views / materialized views refreshed on a schedule. ([posthog.com/docs/data-warehouse](https://posthog.com/docs/data-warehouse), [posthog.com/docs/data-warehouse/sources](https://posthog.com/docs/data-warehouse/sources))

The managed-source catalog is very large (hundreds of connectors; PostHog handles extract and load on your credentials). Confirmed present in the list: **Google Ads**, **Google Search Console**, **Google Analytics**, Google Sheets, Postgres-class databases (Microsoft SQL Server, MongoDB, MySQL family, BigQuery, ClickHouse, Databricks, DynamoDB, Elasticsearch...), HubSpot, Salesforce, Stripe, plus a **Custom REST source**. ([posthog.com/docs/cdp/sources](https://posthog.com/docs/cdp/sources))

Specifics for the two sources the ticket asked about:

- **Google Search Console** — dedicated managed source syncing daily Search Analytics performance (clicks, impressions, CTR, average position) for a verified property; tables by date/query/page/country/device etc., with a `sites` table. ([posthog.com/docs/data-warehouse/sources/google-search-console](https://posthog.com/docs/data-warehouse/sources/google-search-console)) The implementation PR documents Google-side caveats: ~16-month backfill window, ~3-day freshness lag, Google's ~50K rows/(property, date, dimension-set) sampling cap, and query anonymization of low-volume terms. ([github.com/PostHog/posthog/pull/57550](https://github.com/PostHog/posthog/pull/57550))
- **Google Ads** — dedicated managed source syncing Ad, AdStats, AdGroup, AdGroupStats, Campaign, CampaignStats, GeographicStats, Keyword, KeywordStats, Video, VideoStats reports (modeled on the Google Ads BigQuery transformation schema); requires admin access, supports MCC/manager accounts with per-client configuration; default backfill is the last two years. ([posthog.com/docs/data-warehouse/sources/google-ads](https://posthog.com/docs/data-warehouse/sources/google-ads))
- **Generic sources** — the **Custom REST source** connects any REST API via a UI builder: base URL, auth (none / bearer / API key / basic / OAuth2 client_credentials or refresh_token — `authorization_code` not supported), pagination, and per-endpoint "streams" that each become a warehouse table. ([posthog.com/docs/cdp/sources/custom](https://posthog.com/docs/cdp/sources/custom)) Self-managed object storage (S3, GCS, R2, Azure Blob) is read directly on every query. ([posthog.com/docs/data-warehouse/sources](https://posthog.com/docs/data-warehouse/sources))

Ads data also feeds a first-party **Marketing Analytics** product (Google/Meta/LinkedIn/Bing/TikTok/Reddit/Pinterest/Snapchat Ads native integrations, plus BigQuery or self-managed sources with column mapping to campaign/cost/date/source). ([posthog.com/docs/web-analytics/marketing-analytics](https://posthog.com/docs/web-analytics/marketing-analytics))

## 2. Query surface for an agent

- **HogQL/SQL everywhere.** Warehouse tables, PostHog tables, and views are all queryable with SQL (`SELECT * FROM stripe.prod.charge`, joins across sources and events). ([posthog.com/docs/data-warehouse/query](https://posthog.com/docs/data-warehouse/query))
- **Query API.** `POST /api/projects/:project_id/query/` with body `{"query": {"kind": "HogQLQuery", "query": "select ..."}}`. Explicitly supports querying "persons, data warehouse, session replay metadata, and more," not just events. Default 100 rows returned; explicit `LIMIT` allows up to **50k rows per query**; pagination must be keyset (on `timestamp`) — `OFFSET` returns HTTP 400 for personal API keys. ([posthog.com/docs/api/queries](https://posthog.com/docs/api/queries))
- **Not an export path.** PostHog states plainly that `/query` is for ad-hoc analytics/embedded use: bulk or recurring exports are unsupported, connectors built on `/query` "will be rate-limited or rejected," and pipelines on it "may break at any time." Batch exports / file download exports are the sanctioned bulk paths; materialized views are recommended for expensive recurring aggregations. ([posthog.com/docs/api/queries](https://posthog.com/docs/api/queries))
- **Auth.** Private endpoints (including `/query`) need a **personal API key** (scoped, e.g. Query Read), a **project secret API key** (beta, server-to-server, gradual rollout), or **OAuth** for multi-user apps. Public capture endpoints use the project token and need no auth. ([posthog.com/docs/api](https://posthog.com/docs/api))
- **Rate limits** (org-wide, shared across all keys): `/query` **2400 requests/hour**; analytics endpoints 240/min, 1200/hour; general CRUD 480/min, 4800/hour. Orgs *without a paid plan* additionally have "a monthly data-read allowance for queries" — the docs do not state the number (ambiguity noted below). PostHog says it does not offer higher limits, pointing to its "Endpoints" product for query customization and higher limits. ([posthog.com/docs/api#rate-limiting](https://posthog.com/docs/api#rate-limiting))
- **MCP.** The warehouse docs advertise running SQL, managing views, and configuring sources "from Claude Code, Cursor, or any MCP client" via PostHog MCP — a natural agent surface. ([posthog.com/docs/data-warehouse](https://posthog.com/docs/data-warehouse))

## 3. Plan / pricing gates

- The warehouse **is on the free tier**: no credit card, **first 1M synced rows/month free**, then usage-based from $0.000015/row with volume discounts down to $0.000001/row above 1B. ([posthog.com/docs/data-warehouse/start-here](https://posthog.com/docs/data-warehouse/start-here), [posthog.com/pricing](https://posthog.com/pricing))
- **Historical syncs are free for the first 7 days of each new source** (backfills don't burn the row meter during that window). ([posthog.com/pricing](https://posthog.com/pricing), [posthog.com/faq](https://posthog.com/faq))
- Billing meter is **rows synced**, so sync method and frequency drive cost: incremental/append-only syncs and lower frequency reduce billed rows; full-table syncs are the most expensive. ([posthog.com/docs/data-warehouse/cutting-costs](https://posthog.com/docs/data-warehouse/cutting-costs))
- **Sync frequency options: every 5 minutes to every 12 hours to monthly.** ([posthog.com/docs/data-warehouse/cutting-costs](https://posthog.com/docs/data-warehouse/cutting-costs))
- Plan-level gates: Free plan = 1 project, **1 year data retention**, community support; pay-as-you-go = $0 base, 6 projects, 7-year retention. Free-plan usage stops at the allowance rather than billing. ([posthog.com/pricing](https://posthog.com/pricing))

## 4. Limits that force a separate durable store

- **No arbitrary writes.** There is no API for inserting/updating rows in warehouse tables. Write paths into PostHog are: event capture, person/group property updates (public capture endpoints), managed/self-managed source syncs, and CSV/JSON/Parquet file uploads. The warehouse is a *destination for synced copies* of data whose system of record lives elsewhere. ([posthog.com/docs/api](https://posthog.com/docs/api), [posthog.com/docs/data-warehouse/sources](https://posthog.com/docs/data-warehouse/sources)) A GTM harness's own mutable domain records (lead status, owner, next action, agent runs) therefore cannot live natively in the warehouse; the closest native mutable state is **person and group properties**, which are key-value analytics profiles, not relational domain tables with transactional semantics.
- **Read-back constraints.** `/query` caps at 50k rows, forbids OFFSET pagination, and is explicitly not a supported export/serving path — PostHog reserves the right to rate-limit or reject query patterns that look like exports, and recommends "reach out to us" for data-powered APIs. Serving an agent's operational reads at volume from PostHog is against the documented contract. ([posthog.com/docs/api/queries](https://posthog.com/docs/api/queries))
- **Sync latency.** Best case is a 5-minute sync schedule; source-side freshness can be far worse (Google Search Console data lags ~3 days by Google's design). Materialized views refresh on their own schedule on top of that. Not suitable for read-your-writes agent loops. ([posthog.com/docs/data-warehouse/cutting-costs](https://posthog.com/docs/data-warehouse/cutting-costs), [github.com/PostHog/posthog/pull/57550](https://github.com/PostHog/posthog/pull/57550))
- **Retention.** 1 year on the free plan, 7 years on paid — fine for analytics, but PostHog controls the store; it is not a system of record you administer. ([posthog.com/pricing](https://posthog.com/pricing))
- **Rate limits are org-wide** across every API key, so a chatty agent can starve human/API usage of the same org. ([posthog.com/docs/api#rate-limiting](https://posthog.com/docs/api#rate-limiting))
- The workable pattern is the inverse: keep the durable GTM store in Postgres (or object storage), and link it to PostHog as a source — PostHog's positioning explicitly frames the warehouse as the *analysis* layer over external systems of record.

## 5. CRM / "data-in" direction

- **PostHog CRM is a stated ambition, not a product.** Founder James Hawkins opened a public "PostHog CRM" issue (Oct 2024, still open, last active late 2025) proposing deals attached to companies, customizable pipelines, and email/meeting tracking, built on the CDP + groups; he argues PostHog can win by already holding usage/replay/error data. ([github.com/PostHog/posthog/issues/25708](https://github.com/PostHog/posthog/issues/25708))
- Concrete first steps landed via the customer-analytics team: "CRM iteration one" elevated **groups** to first-class (left-nav groups, configurable columns, editable properties, overview tabs, computed properties planned). ([github.com/PostHog/posthog/issues/29881](https://github.com/PostHog/posthog/issues/29881))
- The public roadmap currently lists **Customer analytics** (Product Analytics Team), a **Customer success platform** (Blitzscale Team), **Incoming webhook sources** (Workflows Team — relevant to lead intake as a data-in path), and a **Managed DuckDB Data Warehouse** (ClickHouse Team). ([posthog.com/roadmap](https://posthog.com/roadmap))
- Meanwhile PostHog itself runs its sales pipeline on **Salesforce**, with lead intake flowing from forms/Zendesk/email into Salesforce — evidence its own CRM is not yet dogfoodable. ([posthog.com/handbook/growth/sales/crm](https://posthog.com/handbook/growth/sales/crm))
- For lead intake today, the shipped pieces are: CRM *sources* (HubSpot connector syncs contacts, leads, deals, pipelines, owners into the warehouse — [posthog.com/docs/data-warehouse/sources/hubspot](https://posthog.com/docs/data-warehouse/sources/hubspot)) and CRM *destinations* (e.g. the Close destination upserts contacts/leads from PostHog events — [posthog.com/docs/cdp/destinations/close](https://posthog.com/docs/cdp/destinations/close)). PostHog can mirror and enrich lead data, and push events out to a CRM, but it does not yet *be* the CRM.

## Ambiguities and unconfirmed items

- **"Data-in" as a product name**: could not find any PostHog surface using the literal term "Data-in"; the closest primary-source signals are the CRM GitHub issues, roadmap items above, and "Incoming webhook sources." If the ticket's term came from a talk or newsletter, it has no docs page yet.
- **Free-plan query data-read allowance**: the API docs state that orgs without a paid plan have "a monthly data-read allowance for queries" but publish no number. ([posthog.com/docs/api#rate-limiting](https://posthog.com/docs/api#rate-limiting))
- **Google Search Console source maturity**: the docs page is live, but the implementing PR shipped it behind a feature flag as alpha ("unreleasedSource", `releaseStatus="alpha"`); the docs do not state its current release status, so verify it appears in your project's source list before depending on it. ([github.com/PostHog/posthog/pull/57550](https://github.com/PostHog/posthog/pull/57550))
- **Warehouse table writes**: absence of a row-write API is inferred from the documented API surface (no such endpoint exists in the query/sources/API docs) rather than from an explicit "you cannot write" statement.
- **Project secret API keys** are beta and "rolling out gradually" — availability in a given org is not guaranteed. ([posthog.com/docs/api](https://posthog.com/docs/api))
